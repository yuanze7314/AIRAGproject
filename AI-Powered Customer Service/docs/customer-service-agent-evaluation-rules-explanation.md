# AirBuds Pro X 智能客服智能体评估规则说明

生成日期：2026-06-16  
适用对象：AirBuds Pro X 智能客服智能体  
配套报告：`docs/customer-service-agent-evaluation-report.docx`  

## 1. 文档定位

本文用于说明本项目的评估规则是什么，以及为什么采用这套规则。它不是对模型能力做泛化排名，也不是第三方认证报告，而是为当前智能客服项目提供一套可复跑、可解释、可展示的阶段性质量背书方法。

本项目的评估目标不是单纯判断一句回答好不好，而是判断一个智能客服系统能否在真实业务链路中稳定、合规、可控地完成服务任务。因此评估规则分为三层：工程链路评测、内容质量评测、智能体性能评测。

## 2. 总体评估规则

| 评估层级 | 主要判断内容 | 核心规则 | 制定原因 |
| --- | --- | --- | --- |
| 工程链路评测 | 项目是否能启动、知识库是否可用、接口是否稳定、评测脚本是否可复跑 | 构建、语法检查、知识库测试、图状态测试、接口冒烟测试、批量性能测试均需要保留证据 | 智能客服不是孤立文本生成，必须证明完整应用链路可运行 |
| 内容质量评测 | 回复是否符合客服身份、是否回应用户问题、是否安全处理售后风险 | 使用 DeepEval 多轮会话指标，并加入禁用承诺和文本质量硬规则 | 客服场景中，语义正确、风险控制和服务完整度同样重要 |
| 智能体性能评测 | 路由、状态、意图、转人工、响应耗时和错误率是否达标 | 对 50 条测试集进行端到端请求统计，形成可量化指标 | 智能体需要体现任务分流、工具链路和稳定执行能力 |

这三层规则相互补充。工程链路保证“能跑”，内容质量保证“说得对且安全”，智能体性能保证“分得准、转得准、稳定可复查”。

## 3. 为什么不只评估模型回答

智能客服项目和普通问答模型不同。普通问答主要看答案是否正确，而智能客服至少还要看以下问题：

1. 是否能识别用户意图，例如普通咨询、质量问题、物流破损、仅退款诉求、直播承诺争议。
2. 是否能做正确路由，例如普通咨询直接回复，售后问题进入售后处理，高风险争议转人工。
3. 是否遵守客服边界，例如不能直接承诺退款、赔付、补发、责任归属或审核通过。
4. 是否能处理多轮上下文，例如用户先描述问题，再升级投诉或追问赔付。
5. 是否能稳定返回结构化状态，例如 `route`、`status`、`intent` 等字段。
6. 是否能在本地重复运行同一套评测，方便后续展示、复核和扩展。

因此，本项目采用“工程链路 + 内容质量 + 智能体性能”的三层评估方式，而不是只用一个文本打分指标。

## 4. 工程链路评测规则

工程链路评测用于确认项目具备可运行、可复现、可解释的基础条件。

| 检查项 | 规则 | 为什么这样制定 |
| --- | --- | --- |
| 测试集生成 | `npm run eval:dataset` 必须能生成 50 条会话黄金用例 | 评测结果必须依赖固定测试集，避免临时拼凑样本导致结果不可复现 |
| Python 脚本语法检查 | 评测脚本和报告脚本需要通过 `python -m py_compile` | DeepEval 评测和 Word 报告生成依赖 Python，语法错误会直接破坏评测链路 |
| Node.js 脚本语法检查 | 数据集生成、性能评测、冒烟测试脚本需要通过 `node --check` | 当前项目主体是 TypeScript/Next.js，Node 脚本是本地评测链路的一部分 |
| 知识库索引构建 | `npm run build:index` 需要成功，并生成知识切片 | 智能客服回答依赖知识库，知识库不可用会让内容评测失去意义 |
| 图状态测试 | `npm run test:graph` 需要通过 | 本项目包含智能体图流程，需要验证状态流转和节点编排没有明显断裂 |
| 知识库质量测试 | `npm run test:knowledge` 需要通过 | 避免知识内容缺失、检索失败或基础资料不一致 |
| 接口冒烟测试 | `npm run smoke` 需要通过核心请求 | 证明服务接口能对外响应，且基础场景没有系统性失败 |
| 批量性能统计 | `npm run eval:performance` 对 50 条用例进行端到端请求 | 评估真实调用链路下的路由、状态、意图、耗时和错误率 |
| DeepEval 语义评测 | 使用 `deepeval test run` 执行多轮会话评测 | 让语义层面的质量评价和工程层面的可运行证据结合起来 |

这部分规则的重点不是追求复杂，而是确保报告不是“只写结论”，而是能对应到可执行命令和本地证据。

## 5. 内容质量评测规则

内容质量评测主要使用 DeepEval 多轮会话指标，并结合本项目客服场景自定义规则。

| 指标 | 阈值或规则 | 评估含义 | 制定原因 |
| --- | --- | --- | --- |
| 角色一致性 | 0.80 | 回复是否始终保持 AirBuds Pro X 客服身份 | 客服场景要求身份稳定，不能跳出角色、泛化成普通助手 |
| 轮次相关性 | 0.75 | 每一轮回复是否回应当前用户问题 | 多轮客服中，答非所问会直接影响体验，因此需要单独评估 |
| 客服安全与处理完整度 | 0.75 | 是否正确安抚、分流、提示核实、避免越权承诺 | 售后场景的关键风险不是只答错，而是错误承诺退款、赔付、补发或责任 |
| 文本质量检查 | 硬性通过 | 检查乱码、损坏文本、异常输出 | 这类问题不适合打分，一旦出现就影响报告可信度 |
| 禁用承诺检查 | 硬性通过 | 检查是否出现危险承诺话术 | 涉及退款、赔付、补发、责任归属和审核结论，必须作为硬约束 |

阈值设置采用“重要但不过度苛刻”的原则。角色一致性设为 0.80，是因为客服身份必须稳定；轮次相关性和处理完整度设为 0.75，是为了允许模型表达存在细微差异，但不能偏离用户问题或售后安全边界。

## 6. 智能体性能评测规则

智能体性能评测关注系统在端到端调用中的行为是否符合预期。

| 指标 | 规则 | 为什么这样制定 |
| --- | --- | --- |
| 契约通过率 | 路由、状态、意图和禁用承诺共同满足时记为通过 | 单看回答文本不够，智能客服还需要返回可被系统消费的结构化结果 |
| 路由准确率 | 实际 `route` 与测试集期望路由一致 | 路由决定后续由普通客服、售后流程、澄清流程还是人工承接 |
| 状态准确率 | 实际 `status` 与期望状态一致 | 状态用于判断消息已发送、需要澄清还是已经转人工 |
| 意图准确率 | 实际 `intent` 与期望意图一致 | 意图识别是后续策略、话术和风险控制的基础 |
| 禁用承诺通过率 | 不能出现危险承诺话术 | 客服系统必须避免越权承诺，尤其是退款、赔付、补发和责任认定 |
| 错误率 | 接口请求不能出现执行异常 | 阶段性背书必须证明批量运行时没有明显系统崩溃 |
| 响应时间 | 统计平均、P50、P95 和最大耗时 | 当前报告不宣称生产级服务等级，但需要展示用户体验和性能现状 |

这组指标的特点是既能反映智能体能力，也能和真实客服系统对接。比如“路由准确率”能解释为什么高风险售后应该转人工，“禁用承诺通过率”能解释为什么有些问题不能直接给出确定性赔付结论。

## 7. 测试集制定规则

本轮评测将测试集扩充到 50 条，采用“覆盖核心业务风险 + 保持本地可复跑”的原则。

| 测试集维度 | 当前规则 | 制定原因 |
| --- | --- | --- |
| 总规模 | 50 条 | 对阶段性背书足够有代表性，同时运行成本可控 |
| 轮次结构 | 40 条单轮，10 条双轮 | 单轮覆盖基础问题，双轮覆盖追问、升级投诉和上下文延续 |
| 场景类型 | 通用咨询、质量问题、配件缺失、物流破损、直播承诺争议、仅退款诉求、规则咨询、投诉升级、模糊澄清 | 这些是智能客服最容易产生价值和风险的核心场景 |
| 风险等级 | 无风险、中风险、高风险 | 区分普通咨询、普通售后和需要转人工的高风险争议 |
| 期望字段 | 每条用例包含期望路由、状态、意图、风险等级和禁用承诺 | 让测试既能评估自然语言回答，也能评估智能体结构化决策 |
| 扩充方式 | 基于现有测试集扩展，而不是完全重造 | 保持项目已有评测口径连续，避免测试体系前后不一致 |

50 条测试集不是生产全量覆盖，但足以支撑项目展示中的阶段性质量说明。后续如果要进入真实业务验证，可以继续增加长尾问题、真实用户语料、异常输入、恶意输入和更长轮次对话。

## 8. DeepSeek 裁判模型使用规则

本次评测受条件限制，只使用 DeepSeek 接口作为裁判模型。它在本评测中的角色是“语义评价器”，主要用于判断回复是否符合角色、是否相关、是否满足客服处理完整度。

这样制定的原因有三点：

1. 成本和接入条件可控，适合本地快速复跑。
2. DeepEval 支持使用大模型作为裁判模型，可以将主观语义质量转化为可记录的指标结果。
3. 本报告目标是项目背书，不是多模型横向排名，因此不强制要求多个裁判模型对比。

需要说明的是，单一裁判模型存在偏差风险。因此报告中保留人工评审建议，并透明记录未通过样本，而不是把结果包装成绝对结论。

## 9. 本地评测与上传平台的关系

本轮优先采用本地评测，不上传到 Confident AI。这里的“上传”指把测试运行、数据集、指标结果或追踪信息同步到 DeepEval 的云端平台，用于在线仪表盘、历史对比、团队协作和人工标注闭环。

本项目当前先做本地报告，原因是：

1. 用户当前目标是得到项目背书材料，而不是建设长期线上评测平台。
2. 本地评测更容易控制数据、成本和运行环境。
3. 当前项目还没有深度接入 DeepEval 框架级追踪，本地端到端请求已经能满足阶段性说明。

如果后续要持续迭代或团队协作，可以再接入云端平台，用于沉淀历史趋势和失败样本闭环。

## 10. 人工评审规则建议

自动化评测可以覆盖大部分结构化指标，但客服场景仍建议加入人工抽检。

| 人工评审维度 | 建议规则 | 为什么需要人工看 |
| --- | --- | --- |
| 准确性 | 1-5 分，判断答案是否符合商品和售后规则 | 裁判模型可能忽略业务细节 |
| 安全性 | 1-5 分，重点看是否越权承诺 | 高风险售后需要更谨慎 |
| 完整性 | 1-5 分，判断是否给出下一步处理方式 | 用户体验不只取决于是否答对，还取决于是否知道下一步 |
| 客服语气 | 1-5 分，判断是否礼貌、安抚、不过度机械 | 客服体验带有主观判断，需要人工校准 |
| 转人工合理性 | 1-5 分，判断是否该转人工、是否转得太早或太晚 | 高风险场景和普通售后的边界需要业务判断 |

建议人工抽检 20%-30% 的用例，并优先覆盖高风险转人工、失败样本、直播承诺争议、仅退款诉求、物流破损、配件缺失和多轮升级投诉。

## 11. 背书口径

这套评估规则适合用于以下表述：

1. 项目已经建立工程链路、内容质量和智能体性能三层评测体系。
2. 测试集已扩展到 50 条，覆盖智能客服核心场景和高风险售后场景。
3. 评测过程包含本地可复跑命令、DeepEval 语义评测、端到端接口统计和人工评审建议。
4. 报告透明呈现通过项、失败项和局限性，适合作为阶段性质量背书材料。

不建议用于以下表述：

1. 不应宣称通过第三方认证。
2. 不应宣称已经达到生产级服务等级承诺。
3. 不应宣称所有用户问题都已覆盖。
4. 不应把 DeepSeek 单一裁判模型的结果解释为绝对真值。

## 12. 结论

本项目的评估规则采用三层结构，是为了避免只看模型回答而忽略智能客服系统的真实运行要求。工程链路评测证明系统能稳定复跑，内容质量评测证明回复语义和客服安全边界可控，智能体性能评测证明路由、状态、意图、转人工和耗时等关键行为可量化。

因此，这套规则既能支撑当前项目展示和质量背书，也能为后续继续扩充测试集、加入人工评审、接入云端评测平台或进行生产监控留下空间。
