# 产品简报：内容电商 3C 售后多 Agent 回复决策系统

## 1. 项目定位

本项目是一个面向内容电商平台客服对话窗口的 3C 售后多 Agent 回复决策系统。

它不负责真实退款、退货、补发、赔付或工单流转，而是根据用户文本、上传图片、当前会话上下文和售后规则库，生成一段合规、清晰、可直接发送给消费者的客服文本回复。

第一版目标不是完整售后自动化，而是展示 5 个专业 Agent 在复杂售后对话中的协作能力：案件理解、规则与证据核验、风险与策略决策、回复生成、独立质检。

## 2. 用户与利益相关方

### 直接用户

内容电商平台上的 3C 商品消费者。

典型用户包括：

- 购买手机、耳机、平板、智能手表、电脑配件等商品的消费者
- 因质量问题、配件缺失、物流破损、激活后退货、直播承诺不一致等问题发起售后的人
- 情绪较急，希望平台快速给出解释、处理路径或转人工支持的人

### 间接用户

平台客服与平台售后运营。

他们需要降低重复回复、口径不一致、规则误判和不合理赔付风险。

## 3. 核心场景

消费者在抖音、快手、小红书等内容电商平台购买 3C 商品后，在客服对话窗口中通过文字或图片反馈售后问题。Agent 读取当前输入、历史对话、图片证据和规则库，生成可直接发送的回复。

典型输入包括：

- “手机激活后还能退吗？”
- “耳机用了两天有杂音，我要退款。”
- “包装破了，商品也有划痕。”
- “主播说送充电头，但我收到没有。”
- “我不想退货，你们直接退款。”
- “不给我处理我就投诉。”

## 4. 要解决的问题

### 4.1 售后规则复杂，客服容易答错

3C 类目涉及拆封、激活、二次销售、质量检测、保修、配件、序列号等规则。人工客服只靠经验回复，容易误判规则或过度承诺。

### 4.2 图片证据难以被传统机器人理解

用户可能上传屏幕破损、外包装破损、配件缺失、型号不一致、订单截图、物流截图等图片。纯文本问答无法充分利用这些证据。

### 4.3 高客单价商品需要控制不合理赔付

3C 商品客单价高，Agent 不能轻易承诺“可以退款”“可以赔付”“可以补发”。回复必须区分解释、引导、补证、转人工和最终处理结果。

### 4.4 badcase 难以沉淀

如果某类问题经常被追问、投诉或人工改写，但系统不记录原因，后续仍会重复犯错。第一版需要保留 badcase 记录入口。

## 5. MVP 范围

第一版只做“客服对话窗口内的智能文本回复”。

### 必须包含

1. 平台客服对话窗口：支持文字输入和图片上传。
2. 售后意图识别：识别规则咨询、退货退款、质量问题、配件缺失、物流破损、直播承诺争议、仅退款诉求、投诉升级等类型。
3. RAG 规则检索：从小型售后规则库中检索平台规则、3C 类目规则、激活/拆封/二次销售规则、质量问题规则、配件缺失规则、直播承诺争议口径。
4. 会话记忆：记录商品、问题、用户诉求、图片状态、退款要求、情绪升级、是否已要求补证等关键信息。
5. 图片识别能力：识别破损、包装破损、配件缺失、型号信息、序列号/SN/IMEI、订单截图、物流截图、商品实拍图等线索。
6. 回复策略判断：根据问题类型、规则命中、证据和风险等级选择解释规则、安抚、补证、流程引导、避免承诺、转人工。
7. 文本回复生成：生成语气清晰、有安抚、有规则依据、不过度承诺、说明下一步动作的客服回复。
8. badcase 记录：记录追问、转人工、意图识别错误、规则引用错误、图片识别失败、过度承诺、人工标记等。

### 明确不做

1. 不做真实退款、退货、补发执行。
2. 不做完整售后工单流转。
3. 不接真实支付或赔付系统。
4. 不做物流系统深度接入，可模拟订单和物流状态。
5. 不扩展到全类目，第一版只做 3C。
6. 不做视频或语音识别。
7. 不做自动判责。
8. 不做用户风险画像、信用评分或复杂反欺诈模型。


## 5.1 5-Agent 编排定位

第一版采用 5-Agent 编排架构，而不是单个客服机器人，也不是简单链式 workflow：

1. **Case Understanding Agent / 案件理解 Agent**：先统一建模用户当前消息、历史对话、商品信息、售后意图、情绪状态和图片初步线索，输出标准化案件信息。
2. **Policy & Evidence Agent / 规则与证据 Agent**：基于标准化案件信息并行检索售后规则，判断规则适用性、证据充分度和需要补充的凭证。
3. **Risk & Strategy Agent / 风险与策略 Agent**：基于标准化案件信息并行判断风险等级、是否需要转人工、禁止承诺边界和本轮回复策略。
4. **Reply Agent / 回复生成 Agent**：汇总案件理解、规则证据、风险策略三类结论，生成候选客服回复。
5. **QA Agent / 独立质检 Agent**：独立审核候选回复。只有质检通过才允许输出；不通过则给出修改意见并打回 Reply Agent 重写。

这 5 个 Agent 的协作结果需要在演示界面中可解释展示，让用户看到最终回复不是模型随意生成，而是经过案件建模、并行判断、回复生成和独立质检后的结果。
## 6. 开发深度等级

建议第一版定位为“可展示 AI 产品能力的高保真 MVP”，不是生产级客服系统。

### 深度等级：Level 2.5 / 5

含义：

- 需要真实可操作的前端对话体验
- 需要可演示的 RAG 规则检索链路
- 需要可演示的图片理解链路
- 需要会话记忆和风险策略
- 可以使用模拟订单、模拟物流、模拟售后规则库
- 不需要真实平台、订单、退款、赔付、客服工单系统接入

## 7. 风险控制原则

### 7.1 禁止过度承诺

Agent 禁止直接承诺：

- 可以退款
- 可以赔付
- 可以补发
- 一定通过售后
- 已确认责任方

推荐表达：

- “根据当前信息，建议您补充……”
- “该情况需要进一步核实……”
- “我们可以先为您说明处理路径……”
- “涉及最终退款/赔付结果，需要以平台审核为准……”

### 7.2 图片识别只能作为辅助证据

禁止表达：

- “已确认商品损坏”
- “确定是物流责任”
- “确认缺少配件”

推荐表达：

- “根据您上传的图片，当前疑似存在……情况，仍需进一步核实。”
- “图片中可见……线索，建议您继续补充……”

### 7.3 RAG 必须影响回复但不能替代判断

回复应显示其规则依据来自检索结果，但当规则不匹配或证据不足时，应转向补证或人工，而不是编造规则。

### 7.4 高风险问题优先转人工

高风险信号包括：

- 用户强烈要求仅退款
- 高额赔付诉求
- 激活后退货
- 直播承诺争议
- 用户威胁投诉或舆情扩散
- 图片证据与文本描述冲突
- 规则召回不明确

## 8. 核心回复策略矩阵

| 场景 | 风险 | Agent 策略 |
| --- | --- | --- |
| 普通规则咨询 | 低 | 解释规则，给出下一步 |
| 质量问题但证据不足 | 中 | 安抚，要求补充图片/检测信息 |
| 图片疑似破损 | 中 | 说明疑似情况，引导补充订单/包装/商品图 |
| 激活后退货 | 高 | 解释 3C 激活规则，避免承诺，必要时转人工 |
| 直播承诺争议 | 高 | 引导提供直播承诺证据，转人工核实 |
| 仅退款诉求 | 高 | 不承诺，仅解释需审核，引导平台流程/人工 |
| 投诉升级 | 高 | 安抚，确认诉求，转人工或升级处理 |

## 9. MVP 成功标准

第一版演示成功的标准：

1. 用户能在一个对话窗口中输入文本并上传图片。
2. 系统能展示识别出的售后意图、风险等级、图片线索和命中规则。
3. 系统能生成一段可直接发送给用户的回复。
4. 对高风险场景，回复不会直接承诺退款、赔付、补发或最终判责。
5. 对证据不足场景，回复能清楚要求用户补充什么。
6. badcase 可以被记录，并显示为什么这次回复可能有问题。

## 10. 建议下一步

进入 BMAD PRD 阶段，产出更工程化的需求文档：

1. 明确演示用的 6-8 个售后样例场景。
2. 定义系统模块：对话 UI、意图识别、RAG、图片识别、会话记忆、回复策略、badcase 记录。
3. 定义每个模块输入输出。
4. 定义回复安全约束和验收标准。
5. 再进入架构设计，不直接开始写代码。
